# 專案分析與實用化紀錄（2026-09-06）

## 後續操作體驗修正

針對「資訊太多，找不到重點或入口」的回饋，首頁改為先顯示待處理事項及今日會議，預設只顯示 6 項重點與 5 筆通知摘要；其他重點可明確展開，通知可進入 Inbox。重複的統計、完整工作／服務／同步清單收進詳細區塊，篩選與排序工具預設收合。

側欄分成日常工作與管理功能，首頁提供 My Work、Inbox、Service catalog 三個入口。Catalog 優先顯示服務與套件，團隊管理放在後方；服務、套件與團隊列表提供當前清單搜尋、每頁 10 筆與清除搜尋。這是已載入清單的搜尋，不取代未來可能需要的完整後端目錄分頁。

另修正 Mantine 樣式載入順序與漏載：原本最後載入的 UnstyledButton 重設會蓋掉按鈕底色與邊框，分頁及分段切換也沒有完整樣式。現在使用完整官方套件樣式，修復控制項辨識度。共用失敗畫面增加 Try again。

本輪前端完整 136 項測試及 Fast 驗證通過；後續調整再通過建置與受影響首頁／目錄測試。已以實際瀏覽器檢查首頁的第一屏、按鈕樣式及服務目錄即時搜尋。

## 這個專案到底在做什麼

這是工程團隊的內部工作入口。它將服務目錄、團隊責任歸屬、工作卡、郵件／ERP 訊息、會議與監控結果匯入同一個入口，讓使用者早上先判斷「今天要做什麼、哪些系統出問題、資料同步是否正常」，再進入相關資料或來源系統。

資料整合是核心：外部系統仍然是工作卡、郵件與 ERP 業務資料的來源。Portal 保存可查詢的副本與個人通知處理狀態。現有整合以讀取、匯入和導向來源為主；Portal 的通知已讀不代表 Outlook 郵件已讀，移除通知也不代表 ERP 核准完成。

這已經超過靜態展示網站：有持久化資料、登入、權限、排程、背景執行、失敗重試和整合測試。但能跑展示資料，不等於已經連上公司的正式系統；本次不將測試成功當成正式租戶連線成功。

## 實際架構

```text
瀏覽器 React / Mantine
  └─ HTTP API → Rocket（預設 8000）
                 ├─ 登入、Cookie/CSRF、角色、資料可見範圍
                 ├─ 查詢／修改 → Diesel Async → PostgreSQL
                 └─ 手動匯入／執行／排入佇列

獨立 worker → PostgreSQL 工作佇列／排程／租約
  └─ connector adapter → Azure DevOps / Microsoft Graph / ERP / 監控 HTTP
       └─ 正規化、upsert、同步結果、逐筆錯誤與歷史紀錄
```

開發時 Vite 代理 API；建置後 Rocket 提供 `frontend/dist`，同一個 origin 即可使用。PostgreSQL 同時保存業務資料與工作佇列；目前排程不依賴 Redis。API 與 worker 必須分別運作，單獨啟動 HTTP 服務不會自動處理排隊工作。

| 層次 | 主要檔案 | 職責 |
| --- | --- | --- |
| 資料 | `src/models.rs`、`src/schema.rs`、`src/repositories.rs`、`migrations/` | 使用者、團隊、服務、套件、工作卡、通知、日曆、connector、收件回條、稽核與背景作業資料 |
| 邏輯 | `src/rocket_routes/`、`src/auth.rs`、`src/config.rs`、`src/crypto.rs` | 路由、權限、驗證、登入、加密、API 回應與作業管理 |
| 外部整合 | `src/connector_adapters/` | 各來源的 HTTP 存取、OAuth token 更新、分頁與欄位正規化 |
| 背景作業 | `src/bin/worker.rs`、`src/rocket_routes/connectors/worker.rs` | 排程、claim、租約延長、失敗恢復、心跳與保留期限清理 |
| 畫面 | `frontend/src/pages/` | 首頁、My Work、Inbox、目錄、connector 操作、稽核與詳情 |
| 啟動與維運 | Docker／Compose、`scripts/local-validate.ps1`、`docs/production-runbook.md` | 開發與正式部署、migration、隔離測試、備份和回復程序 |

## 本次直接補上的缺口：完整通知收件匣

修改前，首頁只顯示尚待處理通知，`GET /notifications` 最多回傳 100 筆。雖然詳情已支援移除與稍後提醒，使用者卻沒有完整列表找回那些通知；如果沒有記下 ID 或 URL，就缺少清楚的復原入口。

新增 `GET /me/notifications` 與 `#inbox` 畫面：

- 未讀、已讀、稍後提醒、已移除、全部現存、來源封存六種視圖。
- 在資料庫依標題／內文搜尋，支援大小寫不敏感的文字比對；`%`、`_`、反斜線視為文字。
- 精確來源名稱與嚴重程度篩選；每頁 25 筆，API 可要求 1–100 筆。
- 項目和總數都套用現有資料範圍權限，回條只 join 目前登入者。
- 依更新時間再依 ID 遞減排序，避免時間相同時頁面順序不固定；新增現存通知排序索引。
- 個人標記已讀／未讀、稍後一小時提醒、移除與還原；保留來源已讀狀態。
- 列表條件與頁碼放在 URL，詳情返回及 Microsoft 登入回跳保留有效條件。
- 支援重新整理、空列表、錯誤與重試；操作後最後一頁變空會回到有效頁碼。
- 原有 `/notifications` API 不改回傳格式，保留現有呼叫端相容性。

狀態定義：未讀／已讀排除已移除與尚未到期的提醒；`all` 包含所有尚未被來源封存的通知。`restore` 清除個人移除與提醒，保留已讀狀態，因此還原後可能出現在「已讀」。來源封存只能查看，不會藉由個人還原重新建立來源資料。

分頁是目前資料的 offset 分頁；有新匯入資料時頁面可能位移，不宣稱跨多次 HTTP 請求具有快照一致性。文字包含搜尋目前沒有全文搜尋索引，極大量訊息需要量測後再導入 trigram／全文搜尋。

## 使用方式

1. 完成 migration 並啟動 PostgreSQL、API 和 worker；開啟 `http://127.0.0.1:8000`。
2. 登入後從側欄 **Inbox** 或首頁 **Open inbox** 進入。
3. 預設查看未讀訊息。切到 **Dismissed** 或 **Snoozed**，按 **Restore** 找回已處理的訊息。
4. 用狀態、來源、嚴重程度或標題／內文縮小範圍。按 **Details** 看詳情，按 **Back** 回到原篩選及頁碼。
5. **Archived by source** 用來追查來源完整同步後已不再存在的記錄，與個人移除分開。

本機開發 Compose 會建立示範資料與 README 列出的開發管理員。正式環境使用 `docker-compose.prod.yml` 與既有 production runbook，不能沿用示範密碼或把示範同步當成正式資料驗收。

## 後續應依實際團隊需求優先補足

1. **正式資料驗收**：先選一個團隊，實際接通 DevOps、Graph 與 ERP；核對可見範圍、來源項目數、指派對應、token 更新，以及失敗後恢復。這需要組織的端點與憑證，本次未取得也未假造。
2. **首頁時間與統計**：統一使用者時區下「今天」的定義，涵蓋跨日事件與全天事件；將有限列表筆數與總量區別標示。My Work 目前明示 UTC 到期日。
3. **人員管理入口**：目前使用者建立／維護有 CLI，團隊和來源設定仍需要管理員準備；可再補 onboarding 與權限管理操作流程。
4. **ERP 寫回**：確定 ERP 特定 API、核准規則、冪等與稽核要求後，再做核准／退回；目前 Inbox 不提供可能誤導的「完成核准」按鈕。
5. **主動告警與容量**：現有心跳與失敗資訊可供人查看；若要自動通知值班人員，還需決定接收通道、門檻、去重與告警恢復流程，並針對實際資料量做負載測試。

以上區分了程式碼已具備的能力與公司環境尚需驗收的事情；不能僅憑本機測試宣稱正式系統已可全面上線。
